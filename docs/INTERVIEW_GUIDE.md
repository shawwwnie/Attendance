# CareFlow 면접 설명과 학습 가이드

## 1분 설명

기존에 Java·Spring MVC와 Oracle 기반 서비스를 개발·운영하면서 장애 대응과 데이터 정확성을 다뤘습니다. 이번 공고에 맞춰 Spring Boot·Vue 3·PostgreSQL로 주야간보호센터의 이용 일정과 청구·수납 흐름을 AI와 함께 구현하고 검증했습니다. 특히 중복 청구, 통신 오류 후 수납 재시도, 동시 수납 시 잔액 초과를 막는 부분에 집중했습니다. 월 청구는 수급자 잠금과 고유 제약으로, 수납은 청구서 잠금과 요청 키로 처리했습니다. 실제 장기요양 수가나 공단 연동은 학습 범위 밖이므로 가상 요금으로 업무 흐름을 구현했습니다.

이 문장은 프로젝트를 직접 실행하고 코드를 설명할 수 있게 된 뒤 사용합니다. 실무 Vue·Spring Boot 경력과 프로젝트 학습 경험을 구분합니다.

## 지원동기 구성

제가 강점을 가진 운영 장애 분석과 데이터 정합성 관리 경험으로, 이지케어에 필요한 안정적인 일정·청구 업무 처리를 개선하고 싶어 지원했습니다. 기존 Java 서비스 운영 경험에 Spring Boot·Vue 학습을 더해 현장의 반복 업무와 오류를 줄이는 개발에 기여하고 싶습니다.

## 네 가지 채용 관점에서의 확인 항목

| 관점 | 프로젝트에서 보여줄 근거 | 확인받을 부분 |
|---|---|---|
| 개발팀장 | 실제 API·Vue 연결, 트랜잭션, QueryDSL, DB 동시 요청 테스트 | 잠금 순서·예외 처리·프론트 상태를 직접 수정할 수 있는가 |
| 인사팀장 | 업무 흐름 학습과 실행 가능한 문서 | 새로운 도메인을 학습하는 방식과 이직 이유 |
| 회사대표 | 청구·수납 오류와 운영 추적성에 초점을 맞춘 범위 | 기능 구현을 현장 오류·업무 부담 감소와 연결할 수 있는가 |
| 최종 결정권자 | 동작하는 작은 제품과 명시한 미구현 범위 | 즉시 맡을 수 있는 업무와 적응 기간이 현실적인가 |

## 기술 질문과 답변 핵심

### 왜 Spring Boot를 사용했나요?

내장 서버, 자동 설정, 환경별 설정, JAR 실행 방식이 제공하는 개발·실행 흐름을 확인하기 위해 사용했습니다. 기존 Spring MVC의 Controller·Service 경험은 이어지지만 Boot의 설정·의존성·실행 방식은 별도로 학습했습니다.

### MyBatis 대신 JPA를 사용했을 때 무엇이 달랐나요?

SQL을 직접 호출해 변경하던 방식에서 영속성 컨텍스트와 변경 감지·트랜잭션을 이해해야 했습니다. 엔티티를 응답 JSON으로 직접 보내지 않고 DTO로 분리했습니다. 조회는 필요한 필드를 QueryDSL로 투영합니다. SQL을 보지 않아도 되는 기술이라고 설명하지 않습니다.

### Vue에서 어떤 상태를 관리하나요?

Pinia에는 인증 사용자·센터·알림처럼 여러 화면이 공유하는 상태를 둡니다. 월 필터·모달·폼·조회 결과는 각 화면 또는 composable에 둡니다. `useResource`는 이전 요청이 늦게 도착해 최신 화면을 덮어쓰지 않도록 요청 세대 번호를 비교합니다.

### 중복 청구를 어떻게 막았나요?

서버 트랜잭션에서 수급자 행을 잠그고 기존 월 청구서를 검사합니다. 일정 변경도 같은 수급자 잠금을 사용하므로 마감과 변경이 엇갈리지 않습니다. 마지막으로 DB 고유 제약을 둡니다. 두 HTTP 요청을 동시에 실행해 한 건 생성·한 건 재반환을 검증합니다.

### 요청 키만 있으면 초과 수납도 막을 수 있나요?

같은 요청의 재시도와 서로 다른 두 요청은 별개입니다. 요청 키는 동일 요청을 식별합니다. 서로 다른 키로 들어온 요청은 청구서 행 잠금 후 잔액을 다시 검사해야 합니다. 9,000원 미수금에 각 6,000원인 두 요청을 동시에 보내 한 건만 반영되는 테스트가 있습니다.

### 서버가 두 대라면 어떻게 되나요?

DB 행 잠금과 고유 제약은 같은 PostgreSQL을 쓰는 인스턴스에도 적용됩니다. 다만 현재 세션 저장소는 애플리케이션 메모리이므로 세션 공유 설계가 추가되어야 합니다. 대규모 운영이나 장애 복구까지 검증했다고 주장하지 않습니다.

### 수납 요청 후 응답만 사라지면 어떻게 하나요?

성공 여부가 불명확한 요청 키를 브라우저에 남겨 같은 입력의 재요청에 재사용합니다. 서버에 이미 기록되었으면 같은 수납 결과를 반환합니다. 입력을 변경하기 전에는 청구서의 실제 수납 내역을 먼저 확인합니다.

### 요금은 왜 청구서 항목에도 저장했나요?

수급자의 현재 요금과 과거에 발행한 청구서의 금액은 목적이 다릅니다. 발행 당시 단가·부담률·계산 결과를 저장해 과거 청구의 근거를 보존합니다. 이 프로젝트의 요금은 실제 장기요양 수가가 아닌 가상 규칙입니다.

### 트랜잭션이 실패하면 감사 이력은 어떻게 되나요?

성공 업무 변경과 감사 이력을 같은 트랜잭션에 저장하므로 같이 롤백됩니다. 실패 요청의 원인 추적은 요청 ID와 서버 오류 로그로 합니다. 모든 HTTP 요청을 감사 테이블에 저장하는 구조는 아닙니다.

### 왜 MSA가 아닌가요?

현재 범위는 일정·청구·수납의 작은 업무 흐름입니다. 여러 서비스 사이의 분산 트랜잭션을 추가하기보다 한 DB 트랜잭션에서 규칙을 검증하도록 했습니다. 업무 경계를 이해한 후 독립 배포가 필요한 부분을 측정해 분리할 수 있습니다.

### AI는 어떻게 사용했나요?

요구사항·구현·테스트·문서 작성에 사용했습니다. 결과는 자동으로 신뢰하지 않고 빌드, PostgreSQL 통합 테스트, 권한·동시 요청 테스트와 브라우저 흐름으로 확인했습니다. 면접 전에는 아래 수정 과제를 직접 수행해 설명 가능한 범위를 확인합니다.

## 면접 전 직접 해볼 수정 과제

1. 수급자 일 이용료를 바꾸고 새 청구 금액을 예측한 뒤 검증하기.
2. `Visit.transition`에 잘못된 상태 요청을 넣고 409 응답 확인하기.
3. QueryDSL 검색에 새 조건 하나를 추가하고 결과·전체 건수 함께 확인하기.
4. Vue 일정 화면의 필터·페이지 초기화가 어떤 순서로 동작하는지 설명하기.
5. 동시 수납 테스트에서 잠금을 제거했을 때 어떤 문제가 발생할 수 있는지 토론하기. 실제 변경은 별도 브랜치에서만 실험하기.
6. 수납 취소 기능을 추가한다면 데이터 모델·감사·금액 규칙을 먼저 적어보기.
